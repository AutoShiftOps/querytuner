## Why a follow-up doc, not just a bigger first pass

The original design doc (`docs/querytuner-explain-parser-issue.md`) was built from the ROADMAP's one-line descriptions plus reading the code — it never pulled the actual filed issues' acceptance-criteria checklists, which are considerably more specific than the ROADMAP rows suggested. That's a process gap worth naming plainly: for any future backlog item, check the actual GitHub issue body before scoping, not just the ROADMAP table row.

## #61 — remaining gap

Shipped: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`, `Hash Join`, `Nested Loop`, `Sort` — 7 of the 10 node types the issue lists (confirmed via direct grep of `plan_parsers/postgres.py`).

Missing:
1. **`Merge Join`, `Hash Aggregate`, `Group Aggregate`** — not matched anywhere. These are ordinary node-type strings in Postgres's plan output; adding them to `_NODE_LINE_RE`'s recognized set and `_walk_json_node`'s JSON-side equivalent is the same shape of work already done for the other 7 — no new parsing strategy needed, just more entries in `_INDEX_ACCESS_NODE_TYPES`-style classification (these three are neither full-scan nor index-access; they need their own bucket if `#63`'s cross-referencing is ever extended to reason about join/aggregate strategy, which it currently doesn't).
2. **`EXPLAIN ANALYZE` actual-time/actual-rows parsing** — confirmed via grep that `actual time=`/`actual_time` never appears in the parser. The issue explicitly separates "estimated cost only" (`EXPLAIN`) from "actual rows + timing" (`EXPLAIN ANALYZE`) as two formats to support; only the estimated-cost path is implemented. `PlanNode` (in `plan_parsers/models.py`) would need `actual_rows`/`actual_time_ms` fields, and `_NODE_LINE_RE` needs a second, optional trailing group for the `(actual time=X..Y rows=N loops=N)` segment Postgres appends when `ANALYZE` was used — the regex today has no `$` anchor so it silently ignores that segment rather than erroring, which is why this gap didn't show up as a test failure.

## #62 — remaining gap

Shipped: JSON-only parsing (`EXPLAIN FORMAT=JSON`), deliberately, per the original design doc's reasoning that `QueryInput.jsx`'s MySQL placeholder only shows JSON.

Missing, per the actual issue text (which the original design doc didn't have in front of it):
1. **Plain tabular `EXPLAIN SELECT ...` output** — the issue explicitly lists this as a format to support, independent of what the current placeholder shows. If closing this gap, decide first whether to also update `QueryInput.jsx`'s MySQL placeholder to mention tabular is now supported too, or leave tabular support backend-only for users who paste it despite the placeholder's current JSON-only hint.
2. **`key=NULL` explicitly flagged** ("no index used") — distinct from `type=ALL`; a query can use a suboptimal key or no key at all in ways `type=ALL` alone doesn't catch. Not currently checked anywhere in `plan_parsers/mysql.py`.
3. **`Using filesort` / `Using temporary` warnings** — same gap as `#63` below; these live in MySQL's `Extra` field and aren't parsed at all right now, in either the parser or the cross-referencer.

## #63 — remaining gap (the largest)

Shipped: cross-referencing for the `index_review_*` suggestion family only (join key, WHERE filter, ORDER BY, GROUP BY, partial-index candidates — all from `index_recommender.py`).

Missing, confirmed via grep that none of these type strings appear in `plan_crossref.py`:
1. **`full_scan_risk`** (`sql_analyzer.py:252`) — an existing heuristic, not cross-referenced at all today. The issue's validation trigger ("Seq Scan node or type=ALL present") is actually the simplest of the six to wire up, since `#63`'s existing `_matching_nodes`/full-scan detection already computes exactly this signal for the `index_review_*` types — this suggestion type just needs to be added to whatever set of types `cross_reference_plan()` checks for full-scan confirmation.
2. **`function_in_where`** (`sql_analyzer.py:287`) — validation trigger is "Filter contains function name," which needs the plan node's filter/condition text (not just `condition_column`, which only extracts the column side of a comparison) checked for a function call wrapping the relevant column.
3. **`order_by_no_limit`** (`sql_analyzer.py:313`) — validation trigger is "Sort node with elevated cost." The parser already extracts `Sort` nodes (per `#61`'s shipped coverage) with cost data; this suggestion type just isn't in cross-referencing's scope yet.
4. **`filesort_detected`** / **`temp_table_detected`** — entirely new, MySQL-specific, `Extra`-field-based. These aren't heuristic types that exist yet anywhere in the codebase (confirmed via grep) — this is new detection logic in `sql_analyzer.py`/`index_recommender.py` *and* new cross-referencing, not just wiring existing types in.
5. **Field-naming mismatch** — the issue asks for a `confirmed: bool` (explicitly `false` when no EXPLAIN data, not just absent) and an `evidence` field carrying "actual node data from the execution plan." What shipped (`plan_verified: true`/absent, reused `evidence_level` string, `plan_contradicts: true`/absent) is a reasonable design — matches `evidence_level`'s existing three-tier system rather than adding a fourth, and reuses the exact word (`"schema-verified"`) the UI already promises — but it's a genuine naming/shape deviation from what the issue literally specifies. Worth a product call: keep the shipped naming (recommended — it's more consistent with the existing schema) and update the issue's acceptance criteria to match, or add `confirmed`/`evidence` as additional fields purely for the literal criteria's sake. Recommend the former; don't add a second parallel field system for the same information.

## What shipped against this doc

- **#61**: `Merge Join`/`Hash Aggregate`/`Group Aggregate` now classified and produce a `join_or_aggregate_strategy` Finding (`plan_parsers/postgres.py`). `EXPLAIN ANALYZE`'s `actual time=`/`rows=` segment is now parsed into `PlanNode.actual_rows`/`actual_time_ms` (text and JSON).
- **#62**: Plain tabular `EXPLAIN SELECT ...` now parses (both the pipe-table and `\G` vertical shapes) — `plan_parsers/mysql.py`. `key=NULL` now produces its own `no_index_used` Finding, independent of `type=ALL`. `Using filesort`/`Using temporary` (Extra field, tabular and JSON) now produce `filesort_detected`/`temp_table_detected` Findings. `QueryInput.jsx`'s MySQL placeholder was deliberately left JSON-only per the "decide first" note above — tabular support is backend-only for now.
- **#63**: `full_scan_risk`, `order_by_no_limit`, and `function_in_where` are now cross-referenced in `plan_crossref.py` (whole-plan confirmation, since none of the three carry a per-column `columns` list the way `index_review_*` does). `filesort_detected`/`temp_table_detected` are new, MySQL-only, plan-native suggestions — promoted straight from the parsed plan's findings into `optimization_suggestions` by `sql_analyzer.py`'s new `_plan_native_suggestions`, rather than upgraded via `cross_reference_plan()`, since there was never a pre-existing static-heuristic guess for them to confirm. Field-naming: kept the shipped `plan_verified`/`evidence_level`/`plan_contradicts` shape (this doc's own recommendation) rather than adding a parallel `confirmed`/`evidence` field set — if the literal issue-#63 acceptance text is treated as binding, its wording still needs updating to match, but no further code change is proposed for that.

## Suggested sequencing if this gets picked up

`full_scan_risk` and `order_by_no_limit` wiring into `#63`'s existing cross-referencer first — smallest, reuses signals the parser already extracts, no new parsing work. Then `#61`'s three missing node types + ANALYZE timing (parser-only, no crossref changes). `function_in_where` next (needs filter-text inspection, not just `condition_column`). `filesort_detected`/`temp_table_detected` last — the only piece that's genuinely new heuristic logic end-to-end, not just wiring existing signals together, and MySQL-only, so it also depends on `#62`'s tabular-parsing gap being closed first if filesort/temp-table detection should work from pasted tabular MySQL output too (the issue's `Extra` field appears in both tabular and JSON MySQL EXPLAIN output — decide whether to support both or JSON-only, matching `#62`'s existing JSON-only precedent).
