# Phase 5 — Batch Workload Analysis (#115, #120)

**Status:** Backend implemented (v1) — see "What shipped" below. No frontend UI yet (deliberate — see that section). Two product decisions this doc originally flagged as open have now been made explicitly, not guessed at: (1) Pro-only gating, matching query history/PDF export rather than core single-query analysis; (2) backend-first scope for this pass.

**Original status (kept for history):** Proposed — two related, loosely-scoped issues (checked both bodies directly; neither has an acceptance-criteria checklist, unlike `#61`/`#62`/`#63`). Scoping this required more judgment calls than the EXPLAIN chain did — flagged explicitly below rather than presented as settled.
**Depends on:** Nothing blocking — but genuinely greenfield. Confirmed by grepping the whole backend for "batch"/"Batch": zero matches. No partial code to extend here, unlike every other item this session.
**Goal:** Accept multiple queries at once (either pasted individually or as a Query Store/`pg_stat_statements` export) and produce one reconciled recommendation set instead of N independent single-query analyses that may conflict.

## What the two issues actually say (verbatim, not paraphrased from the ROADMAP row)

**`#115`** (opened by devops-den, no checklist): *"Analyzing queries individually can produce several nearly identical indexes that look reasonable alone but conflict at the table level (over-indexing, write performance degradation). Phase 5 feature — requires new analysis mode that accepts multiple queries and produces a unified index recommendation set."*

**`#120`** (opened by devops-den, explicitly "Related to issue #115," no checklist): *"Accept a batch export from production query history: SQL Server Query Store, PostgreSQL pg_stat_statements, MySQL performance_schema. User runs a standard export query in their DB client, pastes the results into QueryTuner, gets diagnostics on top-N slowest queries ranked by actual production impact."*

Reading them together: `#120` is the *input* half (how multiple queries get in), `#115` is the *output* half (how their recommendations get reconciled instead of just concatenated). Neither works as a standalone feature without the other — `#120`'s batch input with no `#115`-style reconciliation is just running `/analyze` N times with extra parsing work; `#115`'s reconciliation with no `#120` means the only way to feed it multiple queries is pasting them in one at a time by hand.

## What exists today (confirmed by reading the repo)

- Nothing batch-related anywhere — `grep -rn "batch\|Batch"` across `backend/app` returns zero results. `POST /analyze` (`main.py:209`) takes exactly one `QueryRequest`, one query.
- `IndexRecommender.recommend()` (`index_recommender.py:200`) already does real per-query analysis producing `index_review_*` suggestions with real DDL, `columns`, `evidence_level`. This is the thing that needs to run *per query in the batch* — reuse, not rebuild.
- `_dedupe()` (`index_recommender.py:670`) is the only existing "multiple suggestions → fewer suggestions" logic in the codebase, and it's exact-key deduplication *within a single query's own suggestions* (two heuristics both flagging the same column). It has nothing to say about `#115`'s actual ask — reconciling *different* suggestions from *different* queries that touch the same table in overlapping-but-not-identical ways (e.g., query A wants an index on `orders(customer_id)`, query B wants `orders(customer_id, status)` — not a duplicate, but redundant enough that shipping both is the "over-indexing" `#115` names explicitly).
- No parser anywhere for Query Store / `pg_stat_statements` / `performance_schema` export formats — these are three genuinely different formats (SQL Server Query Store is typically a T-SQL result set or DMV export; `pg_stat_statements` is a Postgres system view with normalized query text and `?` placeholders where literals were stripped; `performance_schema` is MySQL's equivalent with digest-normalized text). None of the three give back the exact literal SQL a user typed — they give normalized/parameterized query text, which matters for `#120`'s "paste the export" flow (see non-goals).

## Proposed scope

### `#120` — batch input

1. **New `POST /analyze/batch` endpoint** (or a `queries: list[str]` variant of the existing request — recommend a new endpoint, not overloading `/analyze`'s single-query contract and its existing free/Pro query-count limits in a confusing way).
2. **Three format-specific parsers**, matching the issue's named sources exactly — don't build one generic "paste a batch" box and guess the format; ask the user which source it's from (a dropdown next to the paste box), same pattern `QueryInput.jsx` already uses for per-dialect EXPLAIN placeholders. Each parser's job: extract (query_text, execution_count or calls, total_time or mean_time) tuples — the "ranked by actual production impact" part of the issue depends on having *some* frequency/cost signal from the export, not just the query text.
3. **Normalized-text caveat, explicit**: `pg_stat_statements` and `performance_schema` give parameterized text (`WHERE id = ?` / `WHERE id = $1`), not the literal query a real request used. The existing heuristic engine (`sql_analyzer.py`) was built and tested against real literal SQL — confirm placeholder syntax doesn't silently break column/predicate extraction (`_extract_where_columns` etc. from `index_recommender.py`) before trusting batch results at the same confidence level as single-query analysis. This is a real correctness risk worth a dedicated test pass, not an assumption.
4. **Top-N ranking**: sort parsed entries by whatever cost signal the format provides (`total_time`/`mean_time` for Postgres/MySQL, similarly for Query Store), analyze only the top N (configurable, default something like 20–50) rather than every row in a potentially enormous export — the issue says "top-N slowest queries," not "every query," and running the full heuristic engine against thousands of rows in one request is its own scaling problem worth avoiding rather than discovering in production.

### `#115` — cross-query reconciliation

5. **Run `IndexRecommender.recommend()` per query** in the batch (reusing it as-is, not forking it) to get each query's own `index_review_*` suggestions.
6. **New reconciliation pass** over the combined suggestion set, grouped by resolved real table name (reusing `_resolve_real_table`, the same alias-resolution logic `#63`'s cross-referencing already reused rather than duplicating): for each table, look for column-set overlap across different queries' suggestions — not exact-match (that's what `_dedupe` already handles), but subset/superset relationships (query A's single-column suggestion is a strict prefix of query B's composite suggestion on the same table → recommend only the composite, drop the redundant single-column one) and near-identical composites with different column order (worth a note, not necessarily auto-merged, given `#117`'s column-ordering logic already exists and a "wrong order for query A, right order for query B" conflict is a real scenario this needs to surface, not silently resolve one way).
7. **Output shape**: a reconciled list, each entry showing which original queries it satisfies (so a user can trace "why is this here" back to specific queries in their batch) plus which suggestions were dropped as redundant and why — don't just silently drop things; the whole point of `#115`'s "conflict" framing is making the tradeoff visible, matching this session's running theme of surfacing tension rather than hiding it (same principle as `#63`'s `plan_contradicts`).

## Explicit non-goals for v1

- Not attempting a live connection to pull the export automatically — matches this session's existing precedent (`#57` stays separately scoped for live DB access); user runs their own export query and pastes results, exactly as `#120` describes.
- Not reconciling the *non-index* heuristic types (`cartesian_join`, `function_in_where`, etc.) across queries — those are inherently per-query findings with nothing meaningful to reconcile against each other; only `index_review_*` types go through the new reconciliation pass in v1.
- Not building this as a Pro/Free-tier decision here — that's explicitly called out as still-open in `ROADMAP.md`'s own Phase 5 section (this issue predates that framing); flag it as a decision needed before shipping, don't guess at it in this doc.
- Not attempting automatic detection of which export format was pasted — explicit format selector, same reasoning `#61`/`#62`'s follow-up gave for not auto-detecting EXPLAIN dialect from content alone.

## What's genuinely uncertain here (unlike the last few items)

Both issues are short and undated on implementation detail — there's real design latitude in exactly how "reconciliation" should work (item 6 above is my best read of "unified index recommendation set," not something the issue spells out mechanically). Recommend treating the reconciliation pass's exact merge rules as something to validate against a few real multi-query test fixtures during build, not something to over-specify in a doc before any code exists — this is the one place this session's docs should probably be revised *after* a first pass, not treated as gospel before one.

## What shipped (v1, backend-only)

- **`app/tools/tabular_parse.py`** (new, shared): generic pipe-table/vertical/TSV/CSV row parsing — extracted from `plan_parsers/mysql.py`'s EXPLAIN parsing (which now imports from here instead of a local copy) so `batch_parsers.py` doesn't duplicate it. `parse_pipe_table_rows` now handles both mysql-cli's boxed style and psql's infix-only style in one function.
- **`app/tools/batch_parsers.py`** (new): `parse_pg_stat_statements`/`parse_performance_schema`/`parse_query_store`, each accepting JSON array, pipe-table, TSV, or CSV wire shapes for its one already-selected source (auto-detected — a narrower kind of detection than guessing the source itself, which stays an explicit selector). Normalizes every source's own time unit to milliseconds. `rank_top_n` sorts by total time descending, per #120's "ranked by actual production impact."
- **`app/tools/batch_reconciler.py`** (new): `reconcile_index_suggestions` — subset/superset collapse (drops a suggestion redundant once a wider composite exists on the same table, folding its satisfied queries into the survivor) and column-order-conflict flagging (same column set, different order across queries — surfaced, not auto-merged), exactly the two moves item 6 scoped. Table identity safety is the one place this needed real design judgment — see the module's own docstring for the three-tier alias/schema resolution and why an unaliased suggestion never merges across queries.
- **`POST /analyze/batch`** (new endpoint, `app/main.py`): Pro-gated (401/403/200, same structured-error pattern as `GET /history`). Wires parse → rank top-N → `IndexRecommender.recommend()` per query → reconcile, returning per-query suggestions plus the reconciled/dropped/conflict sets.
- **Real bug found and fixed during this work** (design doc item 3's "dedicated test pass, not an assumption" paid off): `index_recommender.py`'s column extraction never recognized MySQL backtick-quoted identifiers (`` `status` ``) — only double-quoted ones. `performance_schema.digest_text` normalizes every identifier to backtick-quoted form, so every batch entry from a pasted MySQL export was silently producing zero suggestions before this fix. This also fixes the same gap for any single-query MySQL analysis using backtick-quoted identifiers, not just batch mode.
- **38 new backend tests** across `test_batch_parsers.py`, `test_batch_reconciler.py`, `test_analyze_batch.py` (endpoint-level, via `TestClient`, same pattern as `test_history.py`). Full suite: 304 passed, 1 pre-existing xfail, no regressions. Lint and format clean.

**Not built in this pass, deliberately:** any frontend UI (paste box, format dropdown, results view) — this was a backend-first scope call, not an oversight; #120's placeholder/UI question from the original scope section remains open for whoever picks up the frontend piece. Also not built: usage-count integration (Pro users aren't limited, so there was nothing to enforce), and everything the "Explicit non-goals for v1" section below already ruled out.

## Suggested sequencing

`#120`'s parsers first (three independent, parallelizable pieces of work, each testable against real sample export output) — reuse the existing `IndexRecommender` unchanged through this phase, batch input just means calling it N times. `#115`'s reconciliation pass last, since it needs real multi-query suggestion sets from `#120`'s output to test against meaningfully.
